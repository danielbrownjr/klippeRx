# Security model

Approved design v1.0. PC-A-D are required unresolved proposals, PC-E conditional. C1-C3 remain open.

## F02 - Protected provisioning contract

Approved preference: native B3 protected provisioning over confirmed enrolled transport, new designated owner/application authority and platform-owned secret facility. Existing peer bearer access and stored admin/user labels do not establish exclusive owner authorization. Initial SSH host acceptance and secondary certificate acquisition have trust-bootstrap limitations; require verified initial identity and explicit certificate-change reconciliation before sending secrets. Native main-side credential custody must be preserved. Prefer direct enumerated native connect/replace/disconnect/status operations over transferable browser grants when possible. Native entry must be trusted platform code, not an untrusted plugin iframe or script. Automatically provisioned browser-trusted HTTPS is required for private consumer access, including phones, without manual certificate, DNS or proxy setup; it does not replace native protected secret entry unless separately reviewed and approved. Native desktop needed only for install/setup, not continuous service. Native helper does not prove browser trust. Reject ordinary HTTP, manifest JSON secrets, broad bearer delegation, localStorage, URL credentials, same-filesystem encryption as root defense, mandatory broker. No actual provider key, registration or inference in this work.

Logical operations: begin_provision, commit_provision, connection_status, replace, disconnect; names descriptive only. If a grant is necessary, platform creates random high entropy opaque grant over trusted channel with enrolled printer ID, installation ID, application audience, owner principal, provider, permitted operation, current authorization revision, boot epoch, issuance/expiry and unique nonce. Derive principal from authenticated context, never client-supplied owner fields. Recheck authorization immediately before commit. Use operation IDs and durable idempotent status reconciliation after interrupted commit; no blind transport retries or grant reuse. Direct native operation must meet equivalent scoping and replay requirements. Proposed expiry <=120 seconds, atomically consume once, reject on expiry, mismatch, revocation, replay or unsupported platform. No query token, redirect credential, logging, browser-visible daemon bearer or provider key. Native commit transmits credential over pinned protected channel to scoped facility, which binds record to installation/provider/owner epoch. Native UI may hold user-entered key transiently; never expose to plugin/browser JS. Return only status and opaque nonsecret record identifier. No validation provider call without separate explicit user action and later provider gate. Replacement atomically invalidates prior generation and cancels eligible queued work; failures never silently reactivate prior revoked authorization. Prefer platform-mediated fixed provider use with an immutable approved envelope and no generic proxy; scoped retrieval is a candidate only under the approved trusted-adapter boundary with an explicit account of weaker revocation. Secure caller identity is required; local headers do not authenticate a plugin. Selection remains open pending platform evidence and resource review. Secret never enters model evidence. Rate-limit grants and failed attempts; deny if required trust/identity or expiration assurance is unavailable. Use monotonic deadlines for boot-bound grants; offline local analysis must not unnecessarily depend on wall-clock UTC. Review comparison completed at source level; proposed contracts remain unimplemented and C1/C2 open.

## F03 - Application access contract

Private access requires trusted transport, dedicated trusted app origin with a distinct controlled hostname for host-only cookie isolation (scheme/host/port alone is insufficient because cookies ignore port), explicit owner session delegation, independent authorization and backend enforcement. LAN membership, loopback, IP, path-scoped cookies and a successful Moonraker trusted-IP check are insufficient. Native setup alone is insufficient. If browser route lacks trust, block private consumer deployment. A restricted native surface can be evaluated as an engineering alternative, but is not an approved substitute for phone/browser access. Any such surface needs verified assets, isolated rendering and narrow validated IPC, not broad native preload in plugin pages. Public shell/health only minimal liveness/version and inert static content, no evidence, provider state, private IDs or remote assets. Sensitive use requires trusted content delivery. Optional tile only nonprivate launch/status after review. Use exact guarded routes and default-deny backend; static prefix cannot bypass auth. Bind service to loopback if platform supports; untrusted local process access still requires enforcement. Gateway strips client-supplied identity headers and authenticates internal delegation; no trust in spoofable forwarding headers. No generic CORS or credentialed wildcard. Host and Origin exact allowlist, reject missing/null Origin for browser side effects, reject DNS rebinding and ambiguous proxy metadata; document native exceptions as distinct authenticated principal. No state change on GET. Prevent framing private surface; CSP restrictive, text-only untrusted output, no remote scripts, no active model HTML. No secrets or private evidence in URLs or cache; no-store for private responses.

Session grant short-lived, single-use, printer/install/owner/audience/epoch bound, never query string; approved platform transfer protocol TBD. Generate opaque random server-side sessions; rotate at authentication, privilege changes and credential rotation; Secure HttpOnly host-only cookie with appropriate SameSite (prefer Strict subject to tested setup flow), no shared domain; independent anti-CSRF token for state-changing browser requests. No shared-domain cookies; reject cookie injection, ambiguous Host/Origin/forwarded headers, alternate route and direct backend bypass. Require certificate issuance, naming, renewal, expiry and mobile trust acceptance without manual network administration. Proposed idle 15 min, absolute 8 h, grant 120 s; require review and usability acceptance. Logout revokes server-side and terminates private streams; authority revision changes revoke affected sessions, grants and consent. Background polling does not extend idle authority; use monotonic deadlines and enforce absolute expiry, including suspend/resume. Reject expired, stale, cross-printer or uncertain authority; bound backend caches by revocation policy. No automatic session restoration across reboot/recovery until authorization reconciled. Deny direct service requests lacking trusted session/delegation. Exact transport, certificate issuance/renewal and origin mechanism unresolved C1/C3.

| Capability | Authority |
| --- | --- |
| Liveness/version | Public, minimal |
| View private diagnostics | Authenticated app principal with read scope |
| Prepare sanitized preview | Read/preview scope, no export by itself |
| Export | Explicit owner-authorized export scope |
| Dispatch diagnosis | Owner session, CSRF, exact preview digest/provider/account/model/parameters/purpose/revision, one-time short-lived consent and limits |
| Privacy settings | Owner administration |
| Connect/replace/disconnect credential | Protected owner administration, recent auth |
| Printer control / generic proxy | No capability |

Consent bound to immutable sanitized bytes, digest, provider, account, model, parameters, purpose, owner/install identity and authorization revision; one use, proposed <=5 min, invalidate on any bound value change, consume before dispatch, no automatic retry after uncertain billing. Operation status must distinguish unsent, sent and uncertain outcomes; recheck authority immediately before dispatch. Revocation stops future sends but cannot recall sent data. Evidence and provider outputs untrusted; output cannot grant capability. Local operation requires no provider account but does not bypass private access. Proposed response classes unauthenticated 401, forbidden 403, invalid input 400, stale/replay conflict 409 or generic denial, rate 429, unavailable 503; no sensitive error details.

## F04 - Secret lifecycle and isolation

Reported historical U1 daemon and plugin processes run root; data dirs lava-owned; declared data persists after uninstall. Current source correspondence, actual process UID/GID, service identity, mount/namespace and filesystem ownership must be independently inspected. Mode 0600, private venv and colocated encryption are not protection against privileged siblings or root. Same-origin routes are not isolation. Owner approved trusted-administrator and trusted-installed-plugin scope, explicitly excluding hostile root, privileged siblings and shared-UID compromise from confidentiality guarantees. Require distinct controlled browser hostname and supported lifecycle even with residual trust accepted. Stronger confinement is desirable but not mandatory for initial release under this boundary; actual UID/GID, storage, socket and origin behavior still need verification. Published recursive 0755/chown normalization of the persistent B3 and plugin trees means ordinary B3 storage is not an approved vault even under this trust model. Require platform-supported custody and ownership/mode policy preserved across every normalization and repair path. LAN attacker protection is mandatory. No claim of forensic erasure from flash.

Logical authorization state machine (platform-owned durable authority, not backed-up application state): UNCONNECTED -> PROVISIONING -> ACTIVE -> DISABLING -> UNCONNECTED; any uncertain identity/lifecycle -> BLOCKED. Before stop/extraction/uninstall or other authority-affecting lifecycle mutation, platform invalidates relevant authority or blocks access; upgrade/recovery -> BLOCKED pending platform validation; validated normal update may preserve active credential only under approved explicit lifecycle semantics, not restore from backup. Owner approved bounded persistent credentials. Require a daemon-owned authority ledger outside plugin-controlled backup/rollback, protected custody and installation incarnations. Guarantee non-resurrection only for explicitly covered plugin-state rollback, old package and supported restore/recovery paths where the authority remains intact or is invalidated before sensitive access. A whole persistent-image replay restoring ledger, keys and revocation state together cannot be detected reliably by that same local state; no universal anti-rollback claim. No independent freshness anchor established or required by this selected bounded model. Known restoration, missing/corrupt ledger or uncertain identity must block use and require reconnect; disclose that undetected full-image replay is outside the guarantee and remote provider revocation is needed when that risk matters. Persistent mode cannot ship without demonstrated bounded semantics. Volatile reconnect is a possible separately approved fallback, not a silent change. All dispatches check active owner/printer/install/provider generation immediately before send. Linearize revocation against dispatch; cancel queued requests and eligible inflight work; disclose already-sent or uncertain requests. On crash during provision/replace/disconnect, no grant reuse and no active ambiguous key; reconcile via supported platform facility or require new provisioning. No app self-recovery script.

| Event | Required behavior |
| --- | --- |
| Fresh install | No credentials, sessions or consent; local mode only |
| Connect | Scoped protected commit, new generation; no automatic inference |
| Replace | Revoke old generation, no queued sends under old credential; atomically reconcile |
| Disconnect | Disable dispatch first, invalidate grants/sessions and local credential, report failure if deletion not established; remote key remains owner responsibility |
| Normal update | Daemon distinguishes update from uninstall; preserve only compatible active record tied to same owner/install; rotate sessions; fail closed on mismatch |
| Failed update / rollback | No restoration of revoked generations within covered rollback boundary; blocked if authority uncertain; whole-image replay limitation disclosed |
| Uninstall | Daemon invalidates authorization and removes or renders credential unusable; explicit nonsecret evidence retention; no reliance on plugin exit hook |
| Reinstall | New installation identity; disconnected even if nonsecret data remains |
| Backup/restore | Supported backups exclude secrets, sessions, grants and transferable consent; platform ledger excluded from plugin backup; known restore establishes blocked incarnation, restored evidence schema validated and fresh authorization required |
| Firmware recovery | Daemon owns recovery; reconcile identity, no credential resurrection; blocked until validated or reauthorized |
| Ownership transfer | Revoke all grants/sessions/provider connections, apply owner evidence retention/removal policy; recommend owner remote revocation |
| Provider expiry/revocation | Disable cloud on auth failure, no silent fallback; guide owner to reconnect |

Local deletion is not remote API-key revocation. No claim of remote deletion or recall of evidence. Credential canaries must never appear in logs, diagnostics, support exports, backup, UI payloads or model input. Separate secret facility from ordinary declared persistent data. No unsupported custom hooks. Provider credential transport auth is distinct from model evidence.

No contract name is an existing API path, permission or manifest field. C1-C3 remain OPEN. F01-F04 design baseline approved; issue closure is not claimed and no tracker changes performed. C1 requires implemented supported owner/provisioning/access and supported-client evidence; C2 requires protected custody, lifecycle/restore evidence within selected scope; C3 requires actual target UID/GID/filesystem/socket/browser evidence and truthful residual-trust disclosure. Review acceptance and design approval do not establish runtime security.
